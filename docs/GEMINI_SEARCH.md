# Поиск через Gemini: контракт и проверка

Gemini остаётся основным парсером при заданном `GEMINI_API_KEY`. Ни офлайн-словари,
ни совпадение ключевых слов не решают, вызывать ли модель: каждый непустой запрос
до 4000 символов сначала направляется Gemini. Явный `use_llm=False` предназначен
для воспроизводимых тестов. Без ключа приложение показывает предупреждение.

LLM извлекает условия и город в structured output; реальные отели и расчёты берутся
из SQLite, код ранжирует их по параметрам LLM. Затем Gemini объясняет полученную
выдачу. Модель не выдумывает каталог отелей или ответы владельцев.

## Запуск онлайн

В корне репозитория, с ключом в локальном `.env`:

```bash
source .venv/bin/activate
python -m pip install -r requirements.txt
python scripts/check_gemini_search.py --query "Хочу море в пешей доступности"
# Три сценария: море пешком, новая формулировка, смесь известного и неизвестного:
python scripts/check_gemini_search.py
streamlit run app/streamlit_app.py
```

Веб-проверка:

1. Нажмите «Найти» с запросом «Хочу море в пешей доступности».
2. Ожидайте `Разбор запроса: Gemini (онлайн)`; условие — пляж пешком до 15 минут,
   а не вид из окна. Если в БД есть рассчитанные маршруты, выводятся минуты.
3. Проверьте «Хочется засыпать без грохота и видеть морской горизонт из окна».
   Модель должна интерпретировать смысл через доступные характеристики.
4. Проверьте «Хочу тихий отель с телепортом к пляжу»: понятная часть используется,
   неизвестная отмечается как неподдерживаемая. Наличие телепорта не утверждается.
5. При полностью неизвестном пожелании допустим уточняющий вопрос и общий список
   с подписью «соответствие не оценено», а не ложное совпадение.
6. Измените число результатов: пояснение должно соответствовать текущим карточкам.

`ONLINE PASS` означает, что план пришёл от Gemini, есть результаты и не было
резервного объяснения/ошибки. Скрипт возвращает код 1 при fallback: это не онлайн-успех,
даже если пользователю показаны отели. API-запросы расходуют квоту ключа.

## Сбои и деградация

- Валидный план без tasks: код добавляет задачу поиска по критериям модели.
- Неполный JSON-объект: используются валидные поля условий; интерфейс предупреждает
  о восстановлении ответа. Произвольный некорректный JSON не принимается.
- Пустой ответ, невалидный JSON/схема, таймаут, ошибки API: резервный разбор,
  уточнение либо общий список, явное предупреждение с причиной.
- Неизвестный feature: `other`, не новая вычисляемая характеристика.
- Уточняющий вопрос не скрывает доступные результаты. Общий список не означает,
  что неизвестное пожелание выполнено. Явно названный город не подменяется другим.
- Сбой/пустое пояснение Gemini: шаблон из реальных результатов и видимое сообщение.
- Нет отелей в указанном городе или сломана БД: понятное объяснение без пустого экрана.
- Нет рассчитанного времени до конкретной цели: «данных нет», а не подстановка
  общей оценки пешей доступности вместо требуемого ограничения в минутах.

На одну попытку API установлен таймаут 20 секунд; выполняется максимум один повтор
только при транспортной ошибке, 429 или 5xx. Автоматические повторы SDK отключены,
чтобы они не умножались на повторы приложения. План и пояснение — отдельные вызовы.
Ключи, сырые ответы и сетевые адреса не выводятся в диагностике.

При 429 проверьте квоту и ограничения выбранной модели/ключа; немедленные повторные
запуски не гарантируют успех. При 503 повторите позже. При 401/403 проверьте ключ
и доступ, при 404 — значение `GEMINI_MODEL`. Модель автоматически не подменяется.

## Воспроизводимые проверки без API

```bash
python tests/test_gemini_search.py
python tests/test_llm_client.py
```

Тесты используют отдельную БД и подставные ответы Gemini, включая 429/503,
таймаут, неизвестные условия, пустой/невалидный JSON, частичный план, сбой
объяснения и проверки интерфейса через Streamlit AppTest. Это не живые API-тесты.
